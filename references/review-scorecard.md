# 走查评分表

满分 100。**L0 铁律项为一票否决**——任一条不合格，整体判不通过，无论总分多少。

> 使用范围：仅用于标准模式交付前收敛与评审模式。轻量模式与探索 / 发散阶段不打分、不判定可交付性。

## A · 铁律通过性（一票否决，20 分）

| 项 | 分 | 判定 |
|---|---|---|
| 对比度达标（正文 4.5:1 / 组件 3:1） | 4 | 取色器实测，非肉眼 |
| 热区达标 | 2 | ≥ 44×44 或族 1.4 豁免 |
| 主动作可辨 | 2 | 可辨 + 动词短语；并列主动作需已说明理由 |
| 状态完备 | 4 | 5 态齐全 |
| 不丢数据 | 3 | 二次确认 / 可撤销 |
| 一致性（数值有来源） | 2 | 规格内数值均来自 token |
| 动效不阻路 | 1 | ≤ 400ms + 降级 |
| 反馈即时 | 1 | 100ms 内 + 防重复 |
| 输入可恢复 | 1 | 失败保留 + 定位字段 |

任一项为 0 → 判定不通过，先修该项再重评。

## B · 风格执行（25 分）

| 项 | 分 | 判定 |
|---|---|---|
| 风格一致性 | 8 | 同族元素执行统一，无风格噪声 |
| 跨族控制 | 4 | ≤ 2 族，无互斥组合 |
| 风格与场景匹配 | 6 | 符合决策树结论，无场景错配 |
| 细节精度 | 4 | 边框/阴影/偏移量全局统一 |
| 风格克制 | 3 | 装饰不压过信息 |

## C · 布局与响应（20 分）

| 项 | 分 | 判定 |
|---|---|---|
| 四档视口成立 | 8 | 360/768/1280/1920 |
| 对齐与栅格 | 4 | 落在列线上 |
| 留白节奏 | 4 | 疏密有对比，非均匀分布 |
| 密度适配 | 4 | 与定位声明的密度一致 |

## D · Token 完整度（15 分）

| 项 | 分 | 判定 |
|---|---|---|
| Token 覆盖完整 | 6 | 色/字号/间距/圆角/阴影/动效六类齐全 |
| 数值具体可实现 | 4 | 无「柔和」「高级」类描述 |
| 来源标注 | 3 | 区分定律值与风格覆写 |
| 暗色模式 | 2 | 独立色阶，非反相 |

## E · 状态与边界（10 分）

| 项 | 分 | 判定 |
|---|---|---|
| 空态区分 | 3 | 首次/筛选/搜索/权限四态 |
| 边界覆盖 | 4 | 超长文本/0 值/大数值/空集合 |
| 加载与布局稳定性 | 3 | 骨架屏结构一致，无 CLS |

## F · 无障碍（10 分）

| 项 | 分 | 判定 |
|---|---|---|
| 键盘可达 + 焦点可见 | 3 | |
| 语义结构 | 3 | 标签/标题层级/按钮语义 |
| 非颜色信息 | 2 | 状态、图表 |
| 动效降级 | 2 | `prefers-reduced-motion` |

## 判定

| 总分 | 结论 | 动作 |
|---|---|---|
| ≥ 85 | 可交付 | 进入实现 |
| 70–84 | 需返工 | 优先修 A 类未通过项，重跑 |
| < 70 | 方案不匹配 | 回第 1 步重定场景 |

**A 类有一票否决项为 0 → 无论总分多少，一律判定不通过。**

## 返工优先级

修复顺序按用户伤害排序，不按修复难度排：

1. **数据丢失**（破坏性操作无保护）
2. **完全不可用**（对比度严重不达标、热区过小、无法键盘操作）
3. **任务阻断**（状态缺失、流程走不通）
4. **信息误读**（颜色误导、术语不一致）
5. **效率损失**（密度不当、无排序筛选）
6. **视觉一致性**（token 混乱、风格噪声）
7. **审美偏好**（配色喜恶、装饰多少）

第 7 类永远排在最后。评审时若发现「审美问题」占据了大部分意见，说明评分被倒置了。

## 输出格式

```markdown
## 走查结果：XX / 100  [可交付 | 需返工 | 方案不匹配]

### 一票否决项
- [通过] 对比度：正文最低 4.7:1（列表页正文）
- [通过] 状态完备：7 个数据组件均含 5 态
- [不通过] 热区：筛选面板 6 个复选框实际热区 32×32px，位置 3.2

### 未达标项（按优先级）
1. [数据丢失] 批量删除确认文案为「确定删除吗」，未说明影响范围 —— 位置：列表页批量操作栏 —— 改法：改为「将永久删除 N 条记录，不可恢复」
2. [效率损失] 订单列表 60 行无排序 —— 位置：列表页表头 —— 改法：表头加排序

### 加分项
- 数字右对齐 + tabular-nums，纵向比对效率高
- 破坏性操作统一使用 Toast + 撤销而非确认弹窗
```

## 评审模式提示

评审别人的设计时：

- 先列一票否决项，再谈其他——避免用审美意见掩盖可用性问题
- 每条问题必须给**具体位置**和**具体改法**，「不够简洁」不是反馈
- 区分「违反铁律」和「个人偏好」，后者单独标注，不计入总分
- 给返工项排序，明确「先做这三个，其余下轮」
